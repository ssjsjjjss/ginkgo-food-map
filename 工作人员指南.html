一、网站是什么性质

项目说明
定位电子科技大学 Ginkgo 烹饪社内部工具，不是商业产品、不盈利、不接推广
使用者拿到链接的人（默认可看；开启社员口令后才可写）
技术形态一个单页网页应用 + 一个零依赖的 Node 后端（server.js）
数据存储服务器上的一个 JSON 文件 data/store.json（不是数据库）
账号体系没有。免注册，靠「社员口令 + 管理员口令」两级口令区分权限
托管WorkBuddy 应用发布能力，只有一个 HTTP 端口
第三方依赖运行时零（只用 Node 内置模块）；页面只加载腾讯地图底图/搜索 SDK

1.1 权限分三级

身份能做什么
访客（有链接、没填社员口令）看地图、看评价、看排行榜。不能写
社员（填了社员口令）写评价、加店、编辑店铺、回复；只能删自己写的东西
管理员（填了管理员口令）上面全部 + 删/恢复任何人的评价和店铺 + 导入收集表 + 导出备份 + 改口令 + 永久清理 + 设置地图 Key

1.2 必须理解的两条边界

  1. 前端"藏起来" ≠ 后端"挡得住"。

数据管理面板收进管理员口令，只是 UI 层隐藏。真正的防线是服务端强制校验：

  • 所有 /api/admin/* 都要 x-admin-token
  • 写评价/加店在开启社员口令后必须带 x-member-code

改前端代码绕不过去。

  1. 删除默认是软删除（留墓碑、可恢复）；只有「永久清理」才物理删除。

这是刻意的设计：误删可救。deleted: true 的行会继续同步给所有人， store.json 里也会一直留着，直到执行一次 admin/purge。

1.3 已知限制（交接时务必口头说明）

限制影响现状
删除权跟设备绑定换手机后，社员删不了自己以前写的评价owner = meta.deviceId，只存在本地。可改进（见第十节）
昵称 / 口令不跨设备新设备要重填昵称和社团口令存在 localStorage，有意不同步
全量 JSON 写盘数据量大了会变慢见第十节容量表与演进路线
照片以 base64 存在评价行里存储最先被照片撑爆永久清理可勾选清空照片
并发写是"后写覆盖"两人同时改同一条，时间新的赢社团体量基本不会遇到
无服务端分页单次拉取上限 500 条见 4.1；超过会分几轮补齐
「清空全部数据」只清本地点了之后下一轮同步会把服务器内容全部拉回来不是"删库"，也删不掉别人的数据；真删除走管理员接口
「恢复示例数据」只覆盖本地本地店铺目录被 25 家种子店铺替换不会删除服务器数据，但会打断本地未推送的改动

二、架构与运行

2.1 请求链路（一张图看懂）

浏览器
  │  withShareCode() 给每个同源请求补 ?sharecode=
  ▼
平台层（应用发布）：校验 sharecode → 不带就返回「链接不完整」，静态资源直接 403
  ▼
server.js（单端口）
  ├─ GET  /                  → 读 index.html，把腾讯地图 Key 注入 SDK 地址后返回
  ├─ GET  /api/health        → { ok, restaurants, reviews, mapKey, memberRequired }
  ├─ GET  /api/restaurants   → select=*
  ├─ GET  /api/reviews       → select=* / updated_at=gt.X / order / limit
  ├─ POST /api/restaurants   → 数组 upsert（按 id 合并），社员开启时校验 x-member-code
  ├─ POST /api/reviews       → 同上
  ├─ POST /api/admin/*       → 全部要 x-admin-token
  ├─ POST /api/mapkey        → 设置地图 Key
  └─ 其它静态文件 → 直接返回；`server.js / data / build / qa / package.json` 一律 403

2.2 三个"为什么这么写"（改动前先看，否则会踩坑）

  1. 地图 Key 是服务端注入的，前端源码里没有。

Key 存在 data/config.json，在返回 index.html 时替换进 SDK 地址。 所以前端里搜不到 Key，也不会被 /api 泄露。Key 不要写进任何前端文件（有静态测试会卡）。

  1. PWA 图标是内联 data URL，Service Worker 不预缓存任何东西。

因为平台层对静态资源请求会 403（它只给带 sharecode 的主文档放行）， 所以 manifest.webmanifest 的图标写成 base64 内联，sw.js 的 SHELL = []。 别改成外部图标文件，否则 PWA 装不上/图标空白。

  1. package.json 必须存在，但不需要 npm install。

后端零依赖，但发布平台会执行安装步骤，没有 package.json 会直接失败。

2.3 本地跑起来

cd ginkgo-food-map
PORT=3000 node server.js
# 打开 http://127.0.0.1:3000/

与线上的唯一区别：本地没有平台那层 sharecode 校验，所以不用带 ?sharecode=。

2.4 发布到线上

  • 发布类型：http-service，启动命令：node server.js
  • 发布后拿到 https://<domain>/?sharecode=XXXX

2.5 发布前必做的一步（最重要的一条）

rm -rf data      # 删除本地 data 目录

为什么：发布会把整个目录打包上传。如果本地留着 data/，那份本地测试数据会覆盖线上真实数据。 踩过一次，代价是所有人的评价被冲掉。

放心：删的是本地副本，服务器上那份不受影响（发布只上传，不清理服务器已有文件）。

三、数据模型

3.1 存储文件

文件内容
data/store.json{ restaurants: [...], reviews: [...] }，全量、每次写入整文件重写
data/config.json{ admin: {salt, hash, sessions:{}}, member: {enabled, salt, hash}, mapKey }

写入是先写 .tmp 再 rename 的原子替换，中断不会留下半个文件。

字段类型说明

3.3 reviews 行

字段类型说明

scoresobject{taste, value, service, ambience}，各 0–10

3.4 墓碑与孤儿评价

  • 墓碑：deleted: true 的行仍在文件里、仍会同步。这是"能恢复"的代价。

墓碑会一直占用体积，靠永久清理回收。

  • 孤儿评价：restaurant_id 指向一家本地不存在的店。

前端 mergeRemoteReview 会把它丢弃 —— 这正是"只看到默认评价"这类怪现象的根因。 所以同步顺序必须先拉店铺再拉评价（tick() 里就是这么排的）， 永久清理也会顺带清掉孤儿评价。

四、同步机制（出问题先看这节）

4.1 一轮同步做什么

tick() 每 15 秒（pollMs，最小 5 秒）
  ├─ pullRestaurants()  全量拉店铺；本地有未推送改动时，远端不覆盖本地
  ├─ pullReviews()      按 cursor 增量拉：updated_at=gt.<cursor>，limit 500
  └─ push()             只推 待上传队列（pendingRestaurants / pendingSync）里的 id

三个关键点：

  1. pull 靠 Sync.cursor 做增量：cursor 是内存变量（刷新即重置），

所以每次打开页面的第一次拉取都是全量（order=updated_at.asc&limit=500）， 之后同一会话内按 updated_at=gt.<cursor> 增量。 这带来两个结论：

  • 换设备 / 新浏览器 / 刷新页面 = 重新全量拉一遍 → 新设备数据自动就齐，社员无需任何操作
  • 评价总数超过 500 条时，一次拉不完，会分几轮补齐（按更新时间从旧到新）。

到那个量级就该考虑演进方案了（见第十节）

  1. push 只推"待上传队列"，不是全量上传。

写入时把 id 塞进 meta.pendingSync / meta.pendingRestaurants，推成功后清空。 这意味着：只要状态条是绿的，内容就已经在服务器上了。

  1. 照片在本地是 IndexedDB Blob，在云端是 dataURL，两端自动互转

（photoKeyToDataUrl / dataUrlToPhotoKey / adoptRemotePhotos）。 所以照片能跨设备同步，但不进 JSON 快照。

4.2 冲突规则

  • 同一条记录：updated_at 新的赢（服务端按 id 整行 Object.assign 合并）
  • 本地有未推送改动时，pull 不会覆盖它（保护离线编辑）

4.3 照片的两个硬限制

限制位置后果
每条评价最多 2 张，长边压到 1200px，单张 ≤200KB前端 handlePhotoFiles()超了直接丢弃并提示
单条评价照片总量 > 400KB 就只传文字前端 Sync.push()照片不会上传，但文字照常同步

第二条是防网关拒收的兜底。社员反馈"我传了图别人看不到"时，先怀疑这个。

4.4 状态条语义（排障第一手信息）

文案代码条件含义
✓ 已同步到云端 · HH:MM正常已上传、已拉取
离线模式，改动已暂存，联网后自动合并navigator.onLine === false本机排队中
云端同步失败，已回退本地Sync.lastError网络/服务端异常

前两条不需要人工干预，联网后自动补传。第三条持续出现才需要排查。

4.5 关于"社员能不能自己跨设备同步"

能，而且是自动的——因为内容在服务器上，新设备打开链接即全量拉取。 只有一种情况拿不到：内容只存在于某台设备的浏览器里、从未成功推送 （离线写入后一直没联网，或那台设备同步一直失败）。 解决办法不是导出文件，而是把那台设备联网、打开页面、等状态条变绿。

导出 JSON 快照不含照片，所以它只能当文字兜底存档，不能当迁移手段。 文档里必须写清这一点，否则社员会以为导一次就万事大吉。

五、口令与安全

5.1 管理员口令

机制实现
存储config.json 里只存 scrypt 哈希 + 随机 salt，源码里也只有哈希
登录POST /api/admin/login {code} → {token, expiresAt}
有效期7 天（SESSION_TTL_MS）
防暴破同一 IP 10 分钟内 8 次失败 → 429 锁定
改口令POST /api/admin/change-code → 旧会话全部作废并发一个新 token
最小长度6 位

改口令会轮换 salt 并清空 sessions，所以换届改完，所有旧设备立刻掉线——这是特性不是 bug。

口令忘了怎么办：删掉服务器 data/config.json 里的 admin 段，下次请求会用源码里的初始哈希重建（回到初始口令）；或者重新部署一版。

5.2 社团口令（防刷分）

机制实现
开关config.member.enabled，/api/health 里的 memberRequired 会对外暴露
校验点POST /api/restaurants、POST /api/reviews 之前，服务端强制
存储同样只存 scrypt 哈希 + salt，留空 = 关闭
客户端存在 localStorage（ginkgo.member.v1），每台设备独立

关键判断：如果担心链接外流被刷分，只有开启社团口令这一条真正有效。

收起"写评价"按钮、隐藏面板这些都只是 UI，挡不住直接发请求的人。

十、容量与演进路线

10.1 容量参考

规模状态该做什么
< 1000 条评价完全无压力什么都不用做
1000 – 3000 条仍可用收紧图片 + 每学期永久清理
> 3000 条 / store.json > 20MB开始卡换 SQLite
照片多最先出问题优先限制，或挪对象存储

每次全量写盘的成本随体积线性上升，这是当前架构唯一的硬伤。

10.2 三条演进路线（按性价比排序）

方案解决什么大致工作量风险
A. 照片挪对象存储存储体积、同步体积中：评价行只存 URL，前端改上传链路要引入外部存储服务
B. store.json → SQLite写盘性能、并发冲突中：server.js 换持久层，API 语义保持不变需要迁移脚本 + 重新发布
C. 身份迁移（社员自带 ID）换设备后删不了自己的旧评价小：老设备导出一个短码，新设备输入后接管 owner低，但要防滥用（码泄露=删除权泄露）

建议顺序：先做 C（小、直接解决社员的实际痛点），

等真的上三千条再考虑 B，A 在照片成为负担时做。

现在这个体量（几十家店、几十条评价），什么都先别动。
